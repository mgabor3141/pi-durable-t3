# Capabilities

Every call T3's web app makes, and what this host answers. ✅ works · 🔜 next (refused with "… yet") ·
🕐 later · ❌ never (refused on purpose). A refused call returns a message the UI shows. A refused stream
ends with that message rather than hanging open.

| Subagents | a tool call whose `details` carry the `conversationId` of a conversation owned by that call's task (the example's `subagent` tool; pi-durable's convention) | ✅ | projected as T3's provider-native subagent: a `subagent` card in the parent (running → completed / failed / cancelled), an entry in `subagents[]` (prompt and short label from the call's `prompt` / `description` arguments, T3's Task names: another tool's call gets an empty prompt and a generic title; the child's answer as `result`), and a child thread `<parent>.sub.<child conversation>` (derived, nothing stored) with `lineage.relationshipToParent: "subagent"` and `creationSource: "provider"`, so the web app opens it read-only and keeps it out of the sidebar. It is the child conversation's own transcript, live while it runs. Stopping the parent stops the child, and the parent is busy until the child is idle (pi's ownership). Every message, interrupt, undo, rename, delete, model and create write to a child thread is refused with a message (settle, pin and mark-unread are acknowledged as no-ops, as on any thread; archive and disconnect get the generic "not supported"); a client-chosen thread id ending `.sub.<number>` is refused too. The child has no provider session or thread, so "Disconnect agent session" is not offered. | File access | `projects.listEntries`, `projects.readFile`, `projects.writeFile` | ✅ | T3's file panel: browse the tree, open a file, edit and save (the panel autosaves). Every read and write goes through the caller's `ExecutionEnv`, so the panel sees exactly what the agent's `read`/`write`/`bash` see; `stateDir` remains host-only. Replicated from T3's workspace services, with deliberate differences. (1) **Reads are environment-wide:** list, read and search accept any existing directory as `cwd`; writes still require a registered project root or a thread's own folder (a Scratch thread's), compared by real path and exactly, and are refused with `workspace_path_outside_root` elsewhere. T3 checks known roots only on writes. The environment is the boundary, and a paired client can browse anywhere it can reach. (2) **Absolute reads:** a read accepts an absolute environment path; a relative read stays confined to the named `cwd` ('..' and a symlink escape are refused). The picker does not expand `~`: the environment has its own home. (3) **Writes go through the environment:** a write is `ExecutionEnv.writeFile` (parent folders created first), so atomicity and permission-bit preservation are the environment's business; a hard link is written through, a read-only file is refused where the environment refuses it. The symlink checks run before the write: a symlink swapped in between (by something writing inside the root, i.e. the agent) is followed, as in T3. Everything else is T3's: `..` and symlinks out of the root are refused (`resolved_path_outside_root`, symlinks that stay inside are fine), a write never lands in a `.git` or other repository folder, reads return at most 1 MiB (`truncated` says more existed) and a NUL byte in what was read means binary (`binary_file`), `allowMissing` answers `exists: false`, directory listings hide `.git` and mark git-ignored entries (`git check-ignore`; no `ignored` marks when `git` is missing or the folder is not a repository). **Last write wins:** the agent may edit the same file at the same time and there is no merge or conflict check, as in T3. Gated by the session's scopes as T3 gates it: `filesystem:read` to list/read/search, `filesystem:write` to write (a standard pairing holds both; a narrowed one, minted in Settings → Connections, may not). Previewable files are served by `assets.createUrl`; text files still go through `projects.readFile` |
