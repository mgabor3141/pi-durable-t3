# Capabilities

Every call T3's web app makes, and what this host answers. ✅ works · 🔜 next (refused with "… yet") ·
🕐 later · ❌ never (refused on purpose). A refused call returns a message the UI shows. A refused stream
ends with that message rather than hanging open.

| Area | Calls | | Notes |
|---|---|:-:|---|
| Connection & config | `server.probe`, `server.getConfig`, `server.getSettings`, `server.refreshProviders`, `server.reportClientActivity`, `subscribeServerConfig`, pairing, tickets | ✅ | `getSettings` answers T3's settings document; the config stream pushes `settingsUpdated` |
| Connections (pairing & devices) | `/api/auth/pairing-token`, `/api/auth/pairing-links`, `/api/auth/pairing-links/revoke`, `/api/auth/clients`, `/api/auth/clients/revoke`, `/api/auth/clients/revoke-others`, `subscribeAuthAccess` | ✅ | T3's Settings → Connections, server side, replicated from the pinned T3 (`apps/server/src/auth/{EnvironmentAuth,SessionStore,http}.ts`): a paired owner mints a one-time pairing link (scoped to its own grant), lists the paired devices, and revokes a link, a device, or every other device. A device list marks the caller `current` and a live socket `connected`; the access stream sends a snapshot then live upsert/remove events; revoking a client also closes its live WebSocket. A device cannot revoke the session it is calling with (403) |
| Shell & thread reads | `orchestration.subscribeShell`, `orchestration.subscribeThread`, `orchestration.getThreadProjection`, `orchestration.launchThread` | ✅ | projects ride the shell snapshot |

| Model & thinking | `modelSelection` on create/launch/prompt, `thread.model-selection.set` | ✅ | passed through. Thinking is T3's `thinking` option, offered only for models that reason. A run's model is read from the message pi recorded |
| Crash resume | `message.dispatch` and the resumed run | ✅ | see the clip in the README |
| Sidebar bookkeeping | `thread.visit`, `thread.mark-unread`, `thread.settle`, `thread.unsettle`, `thread.auto-settle`, `thread.auto-settle.set`, `thread.pin`, `thread.unpin`, `thread.pin.reorder`, `thread.active.reorder`, `notification.delivery.accept` | ✅ | acknowledged; T3 keeps these client-side |
| Projects | `projects.mutate` (`project.create`/`update`/`delete`), `projects.ensureScratch`, `/api/projects/mutate` | ✅ | ids honored, the same folder can't be added twice, removing a project removes its threads but not its files. `ensureScratch` is T3's "No project": it re-creates the host's configured scratch dir and finds-or-creates the project rooted there, answering its id; the config advertises the folder as `scratchWorkspaceRoot`, and a thread launched there runs in a folder of its own under it, named as T3 names it (date, the first message's words, the thread id) and reported as the thread's `worktreePath`. A host with no scratch dir advertised: the entry is refused and the config carries no `scratchWorkspaceRoot`, so the client offers no such thread |
| Thread launch in a worktree | `orchestration.launchThread` with `workspaceStrategy` `worktree`/`existing_worktree` | ❌ | no git worktrees on this host: `root` is honored, every strategy runs at the project root (a Scratch thread's own folder is the bridge's claim, not a worktree) |
| Settings | `server.updateSettings` | ✅ | T3's merge and validation, replicated. Not replicated: per-key special cases, secret redaction, provider history |
| Folder picker | `filesystem.browse` | ✅ | directories only, for Add project |
| Thread fork | `thread.fork`, `thread.merge_back` | 🔜 | undo already forks |

| Queued messages | `queued-*`, `queue.resume` | 🔜 | pi-durable has the queue; editing it from the UI is missing |
| Attachments | `attachments.*`, `assets.*` | 🕐 | prompts are text; no asset store |
| Thread search | `orchestration.searchThreads` | ✅ | T3's command-palette / sidebar thread search ("search thread messages"), answered from the conversations this host has. Replicated from T3's server `ThreadSearch.ts`: an ASCII-case-insensitive substring over every user/assistant message, one best match per thread (a user message first, then newest, then lowest id), threads ordered user-first then most-recently-updated then thread id, capped at the limit, with T3's snippet. A scan of the head conversations on each query — no persistent index (see known limitations). The search box also matches a thread's title on the client, from the shell data it already has |
| File search | `projects.searchEntries`, `projects.searchContents` | ❌ | the file-content search (a separate feature from thread search): the UI shows it only when the grant has `filesystem:read`, and it reads files — refused with the rest of file access; the agent reads files itself |
| Usage | `server.getUsageSummary`, `server.refreshUsageRates` | ✅ | The usage page, answered from what pi-durable records per turn (tokens, cost, model on each assistant message). The day/hour bucketing, de-duplication (a fork that shares an entry is counted once), window checks and `costSource` resolution are replicated from T3's `usageAggregation.ts`; the field mapping from pi's `Usage` mirrors T3's own pi reader. Cost is pi's own reported figure (`providerReported`), and a turn pi priced at zero is `unpriced` — never a LiteLLM estimate. Not replicated: LiteLLM model-rate pricing and cache-savings (this host fetches no rate table, so `refreshUsageRates` reports pricing `unavailable` and cache savings are `0`); fast/ultrafast speed tiers (pi has none) |
