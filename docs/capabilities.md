### MCP

Authenticated as T3 does it: an MCP client signs in over OAuth (`t3/mcp-oauth.ts`, T3's `McpOAuth`): RFC 9728 and RFC 8414 metadata, stateless dynamic registration (a signed client id; up to 10 redirect URIs since 0.1.11, the id capped past five so the authorize URL fits; metadata that is not JSON or not the contract's shape is RFC 7591's `invalid_client_metadata`, "Invalid client metadata: …"), the authorize redirect into the web app's `/connect-agent` page, approval with a pairing code or one click from a signed-in browser (CSRF-bound), and a PKCE (S256) code that lives 60 s and is spent once. The token is an `mcp-client` session for 30 days, at the access the user chose (`read-only` … `full-access`); a peer link's is moved back out to 30 days by a call that finds it a day short, and every answer to it says until when (`t3-link-expires-at`, T3 0.1.11). `/mcp` accepts only those sessions, and they are refused everywhere else (T3's audience split).

A request without one gets 401 with T3's `resource_metadata` challenge. Such a client has no calling thread: it reads, and writes within its access, as T3's `writesThreads`. Every thread here runs at `full-access`, so a client approved below that may not write, and gets T3's `runtime_mode_escalation_denied` (in 0.1.11's words: the thread's modes and the caller's limit).

Reads are T3 0.1.11's (`t3_thread_read`, `t3_thread_list`): ten items or threads unless asked, 500 characters an item, and a read result cut to 30,000 bytes from the end it pages toward (an item larger than that alone has its text, then its title, cut); a client reads forward from a cursorless read (`afterPosition`, `nextPosition`), and `beforePosition` pages back with `earlierPosition`; a `projectId` that does not exist is named. Since 0.1.11 a thread in a list or read carries `pinned`, `snoozed` with `snoozedUntil` (T3's `isSnoozed`: a snooze still ahead that no approval, newer question or failed run has woken), `blockedOnThreadWait` and `pendingBackgroundTasks`, from the shell, which T3's sidebar reads too: blocked while every row its running turn still works on is `thread_wait` or a `thread_prompt` that waits (T3's `t3_thread_wait` and `delegate_task` in `wait` mode), and background work is the `thread_prompt` children that still work after the turn that started them ended (T3's subagent tasks, `derivePendingBackgroundWork`), which make the thread's status `waiting` unless its run failed; this host has no background commands or monitors to list. A thread link passed as a `threadId` (T3's `t3-thread://` link, or the web link this host gives a client) is answered with the id to pass. `t3_thread_wait` waits 30 s unless asked, at most 45 s, before a common MCP client's timeout.

### Thread tools

Our design, not T3's: one entity (the thread), one parent link, one result (gmux's exchange report: every message that entered the activity, the tool-call count, the final answer, with the verdict beside it). `thread_prompt` starts a child (a thread with `lineage.relationshipToParent: "subagent"`, `forkedFrom` its card's node, and `spawn` on its record; optionally with the caller's history, `fork`) or follows up on any thread, with `mode` `auto \| followUp \| steer \| notify` (`notify` adds the message to context as an `app.note` entry, starting nothing). It waits for the activity (until it settles, unless a `timeoutMs` is given), or returns at once and asks to be answered, delivered as T3 delivers a delegated task's completion: when the activity settles, the report is posted into the caller's thread (`createdBy: "agent"`, `creationSource: "server"`, `senderThreadId` the child when it is one report), as a steer into its running turn (pi steers without interrupting tools) or starting a turn when it is idle; never interrupting or restarting a turn.

A wait that runs out turns into the same request, held, as T3's `settled_only`, until the caller's turn that asked has ended, and then queued. A report that settles while an earlier report message still waits in the caller's queue joins that message: one message, one turn. A report the caller collects itself (`thread_wait`, `thread_read` of the child's latest exchange, or a prompt that waits) answers its requests: they are withdrawn and nothing is posted; while the caller waits for a child, that child's report is held.

One already posted and still waiting in the caller's queue is taken out of its message, and a message left with none is cancelled, as T3 acknowledges a task's result. Requests live on the receiving thread's record until delivered, and delivery is keyed by the request, so a restart delivers each once. The parent shows each child as T3's `app_owned` subagent card in the run that started it, from the child's live shell or the outcome its record keeps.

`thread_cancel` interrupts a thread and its children and drops the reports within that subtree. Limits: 3 levels deep, 10 busy children per thread. The same extension carries T3's `schedule_task`, `list_scheduled_tasks` and `delete_scheduled_task`, its project tools `t3_project_list`, `t3_project_read`, `t3_project_create`, `t3_project_update` and `t3_project_delete`, and `t3_thread_update`, `t3_thread_organize`, `t3_queue` and `run_scheduled_task_now` (row above), acting as the calling thread (no `threadId`: its own); the project tools' descriptions add what this host's projects are (a title and a folder; a new root moves no files and no threads). `/mcp` keeps T3's names (row above)

### Sidebar state

A settle is refused, in T3's words, for a thread that is running ("is still running. Stop it before settling.") or that holds a message someone queued ("has a queued message. Send it or remove it from the queue before settling."): a person's, not an agent's, a report's or (0.1.11) a scheduled task's. T3 also removes a settled thread's queued notes, reports and scheduled prompts, which here stay queued and wake it when they run. Since 0.1.11 a settle also turns off a provider limit's auto-resume and snooze (a settled thread refuses recovery, in T3's words: "The thread is settled. Un-settle it to resume at the reset.").

Settle and un-settle are advertised as `threadSettlement`, the per-thread opt-out as `threadAutoSettleOptOut`: settling drops the pin and the dragged place, pinning a settled thread makes it active, new activity wakes a settled thread. T3's settlement sweep runs every minute and on a settings change: a thread quiet for longer than its project's `sidebarAutoSettleAfterDays` (default 7 since 0.1.9) settles as of when it went quiet, unless pinned, kept active, switched off or running. A subagent thread (a `thread_prompt` child) has no days of its own since 0.1.11: it stays while its parent is live and not settled or archived, then settles as of that sweep, even with automatic settlement switched off. Unlike T3's rule, being made counts as activity whatever messages a thread has: a fork starts on its source's turns, which can be weeks old, and would otherwise settle the minute it is made. A thread moved back to old turns (`/undo`, `/tree`'s "Go here") has no such time and can settle at once. Pull requests, which also settle threads in T3, do not exist here.

`notification.delivery.accept` (T3's mobile push receipt) is acknowledged. Tags (T3 v0.1.7) are kept on the record in the order added, an add is idempotent, and the shell carries `tags` only when there are some, as T3's; T3's settings hide tagged threads client-side. Pinning a settled thread stamps its un-settle (`unsettledAt`); undoing a settle (`thread.unsettle` with `restoreUnsettledAt`, 0.1.10) puts back the stamp the settle cleared, so the thread returns to its place, and an anchor that is not a time is refused in T3's words. `thread.settle` with `expectedLatestRunId` (0.1.9) is refused when another run has started since.

A thread's own agent settling it mid-turn (`t3_thread_organize`) follows T3's `settleAfterRun`: after the turn it waits for subagent reports still running, leaves the thread active if a person wrote to it or a report's run failed, and names the latest run in the settle

### Thread titles

A launch stores its `title`. Generation is the integrator's `titleThread` hook; without it `threadTitleRegeneration` is not advertised and `regenerateTitle: true` is refused. Titles are durable; the in-progress marker is in memory. `branch`, `worktreePath`, `expected*` and `linkedPullRequest` are refused (no git, no PR backend); `limitRecovery` is the row "A provider's limit, resumed at its reset". No retries of a failed generation (T3 retries "initial" twice): the hook's to do. T3's text-generation model (Settings → Threads → Text generation model, `textGenerationModelSelection`) reaches the hook as `request.model` when it names one of this host's models, with its thinking level, and `T3Attachment.textGenerationModel()` answers it for the integrator's other generated text; unset (the stored default is T3's Codex model) or a model this host lacks: absent, and the thread's own model is used.

T3's title instructions (`threadTitleInstructions`), when set, reach the hook as `request.guidance` (trimmed, at most 20,000 characters), for the title prompt after the conversation, under "Additional instructions", as T3 places them.

Since 0.1.11 the hook is told the project's title (`request.projectTitle`), which T3's generator is told to leave out of the title, and a side chat is titled from its own messages: `request.after` is the entry it was opened at, and the history up to it, its main thread's, is not its subject (the example hook reads the entries after it). A regenerate ends as T3's does: `renamed`, `unchanged` (no title, "New thread" or the same one), or `failed` with the last line of the hook's error (at most 300 characters; "Title generation failed." when it has none), "This thread has no messages to title yet." (nothing of its own after the side chat's start) or "This thread's project no longer exists.". A first title reports no outcome, as in T3.

### Idle compaction

A turn's usage reports the lifetime its last request's cache was written with (the provider's one-hour tokens, else the short one) and when it expires, counted from the request. With Settings → Providers → "Compact idle threads" on "Before the cache expires", a run that completes sets a timer for 2 minutes before that expiry; then the thread is looked at again and, if it is still one to compact, `/compact` is sent as T3 sends it (`createdBy: "agent"`, `creationSource: "server"`, `idleCompaction: "beforeCacheExpires"`), so the summary is still made from the cache where the integrator's summarizer reads it. Left alone, as in T3: a context under 200,000 tokens, a thread archived, settled, snoozed or deleted, a side chat, a latest run that did not complete or is itself a compaction, a pending request, a fork waiting to be brought back; and here also queued messages and child threads that still work, which is what T3's pending background work comes to.

The timers are in memory, but what they wait for is not: when the bridge starts, and when the setting is turned on, the threads whose latest run completed within the longest cache lifetime are looked at and armed again (T3's own timers are lost on a restart). "When you return" (T3's default) is the web app's doing and it does it for Claude threads only, so it is not offered here; per-provider overrides are Claude's too

### A provider's limit, resumed at its reset

A reset within 5 hours is waited for (`autoResume`), and with T3's setting "Auto-resume limited threads" (`autoResumeLimitedThreads`) any reset is, however far; T3 itself waits only with that setting, and its "Snooze limited threads" is not acted on: 30 seconds after it the run is continued with no message written, as `/continue` does, and T3 shows "Usage limit reached · Resumes 9:40 PM" with "Cancel auto-resume". A later reset ends the run ("Resets …"), and T3's "Resume at reset" asks for the same wait; "Snooze until reset" hides the thread until then. While a thread waits, a message sent to it starts nothing: it is queued as behind a run (a steer joins the run when it is continued, the others follow it), the thread's latest run stays the limited one (T3's `latestUnheldRun`), and whoever waits for the thread (a parent's report, `thread_wait`) is not told it failed.

Resume, `/continue` and "Send now" go on at once and end the wait. If something else was written to the thread by the reset, nothing is continued and what is still queued starts. The timer is set again from the thread record after a restart; a reset that passed meanwhile is acted on at once.

A request that reaches the limit again when it is continued starts the same over. Unlike T3 there is no `requestId` on the recovery, and an error without the provider's wait (another provider's 429) has no reset time: it is retried

### Undo and redo

Both move the thread's head to a fork that ends before what is taken back; the conversation left behind keeps everything. `/redo` returns the head to it, one undo at a time, newest first, T3's own Revert included, while nothing was written since the undo (the fork still ends where it was made) and no turn is owed. The model's context is what changes: files, anything done outside the conversation and threads the agent started stay. `/redo fork` opens it as a new thread instead (a fork of this one, titled "… (before undo)"), and leaves this thread as it is: it works when the thread has gone on since the undo and `/redo` is refused, which then says so.

What the integrator keeps of the turns outside the conversation (memories written from them) is not told of an undo and stays. Refused while a turn runs or messages are queued, past a compaction, and for more turns or steps than there are.

### The thread's tree

An undo leaves the conversation it moved from whole, so a thread that was undone and written on again has several lines that share their turns up to where they part. `/tree` reads every conversation the thread has had as its head (the last 50 undos, redos and moves are on its record), each only down to the first entry another has too, and shows their turns as one tree: the line the thread is on as a column, a line that parts from it indented under the turn it parts after. A turn is a message of the user's and what followed; a turn that two lines cut at different places (`/undo step`, then something else) is two rows. It is shown as a command's answer is: in memory only, never sent to the model, gone when the host restarts.

Everything that shares history with the thread is in the tree, however it came to be. Besides the conversations the thread's own record names (its head and its last 50 undos, redos and moves), every conversation forked from one of them, or they from it, is read, by pi-durable's own fork links (one scan of the conversation records): another thread's lines, a line left long ago, a line whose thread was deleted, a line no record names. No thread record has to be right for a line to be found. The turn each other live thread is at carries that thread's title; a fork that has written nothing is named on the turn it was made at, and a deleted thread's line has no name. A thread that began on its own (a child an agent started with no history) shares nothing and is not there. "Go here" and "Fork" work on any row: going to a turn of another thread moves this thread there and leaves that one alone.

A line that shares no turn with the thread's own (the thread was taken back to before its first message and begun again) is shown first, however far down the thread is; work a line has before its first message is a row of its own.

A long thread is shown a window at a time: six turns each side of where the thread is and the first three of each line that parts, with buttons for 25 more.

T3's frame gives the page an opaque origin and no session, so its buttons cannot call what the app calls. They post to `/api/thread-nav` with a token made for the page (random, in the page's source, good for 30 minutes after its last use, in memory only), which is all the route checks. The host's CORS answers its own origins only, so the page cannot read the answer: every action shows the page again in its place, as a new file, with what happened said in it; a page whose token is gone says after eight seconds that nothing happened. The file before the last is kept for a client still loading it, older ones are removed.

A step is a response the model was given back (a failed or cut-off request is not one). The commands and their answers are shown only, as `/context` is: written to the head, they would be the first thing a redo loses. On a thread an undo emptied there is no run for the command to stand in, so only the answer is shown; T3 keeps its own copy of the sent command on screen until the thread is left

### Scheduled tasks

A run is recorded as succeeded once it is dispatched — a new thread with the prompt as its first message (shown as "Sent by automation"), or the prompt queued on the task's thread — and then, as T3 0.1.11, followed to its end for up to a day, by its message (`bridge.waitFor`; a queued message's run is renamed when pi places it). A run that completed at or after a one-time task's time removes the task (its thread stays; a run by hand before the time keeps it, paused or not). A run that did not complete marks the task failed, with its provider's error, or else T3's "The run failed.", "The run was stopped." (a Stop), "The run was cancelled." (removed from the queue) or "The run was rolled back."; a queued message sent as a steer joins the run it steers, and nothing is recorded. Either only while the task still shows that run. The following is in memory, as T3's is: a host that restarts meanwhile forgets it, and the task keeps what the dispatch recorded. Deleting a thread deletes the tasks bound to it (T3's `scheduled-tasks.cleanup` effect, `deleteForThread`); a thread deleted outside T3 leaves its tasks failing on every run. A task left running by a crash is recorded failed and rescheduled. A fixed-time run missed while the host was down is skipped and, since 0.1.10, recorded as the task's last run, failed ("Missed a scheduled run because the server was not running at that time."). The list names the host's time zone (`timeZone`, 0.1.11), which T3 shows in a fixed time's label. As T3 0.1.11, a recurring task does not queue its prompt on its thread again while the last copy still waits there: that run is skipped, and when the queue is held (after a Stop) the task records it as failed ("A previous occurrence is held in the thread queue. Resume or remove it to run this task again.").

Stored in the Harness's storage beside the threads. Every run is at the project root. A worktree request on a folder that cannot hold one, Scratch or a folder that is not in a Git repository (`git rev-parse` through the environment, as T3 asks it), is stored as the root, as T3 0.1.11 stores it; on a Git repository it is refused (T3's form defaults to one; pick "Use the project checkout"). A run queued on the task's thread follows the thread's current model, as in T3; the task's model seeds new threads only. A task asking for approvals or plan mode is refused, as the thread commands are (T3's form never asks).

The launched thread carries the task's title, as T3's launch does (no generated title: T3's scheduled launch asks for none). One-time tasks (`{ type: "once", runAt }`, T3 v0.1.7, advertised as `oneTimeSchedules`): stored as UTC, run once at their time and never again, a manual run before it does not use it up, and an enabled one whose time has passed is refused on save or enable with T3's message. Thread modes (0.1.9; `scheduledTaskThreadModes` is advertised): a new thread each run, or one thread that continues, which the first run makes and the task then keeps (`bindThread`); a destination must be a live, unarchived thread of the task's project. "One thread, fresh session each run" (`fresh_session`, `freshSession` on `schedule_task`) is refused on save: no thread here can drop its context

### File access

Every read and write goes through the caller's `ExecutionEnv`, so the panel sees exactly what the agent's `read`/`write`/`bash` see; `stateDir` remains host-only. Replicated from T3's workspace services, with deliberate differences. (1) **Reads are environment-wide:** list, read and search accept any existing directory as `cwd`; writes still require a registered project root or a thread's own folder (a Scratch thread's), compared by real path and exactly, and are refused with `workspace_path_outside_root` elsewhere. T3 checks known roots only on writes. The environment is the boundary, and a paired client can browse anywhere it can reach. (2) **Absolute reads:** a read accepts an absolute environment path; a relative read stays confined to the named `cwd` ('..' and a symlink escape are refused). (3) **Writes go through the environment:** a write is `ExecutionEnv.writeFile` (parent folders created first), so atomicity and permission-bit preservation are the environment's business; a hard link is written through, a read-only file is refused where the environment refuses it.

The symlink checks run before the write: a symlink swapped in between (by something writing inside the root, i.e. the agent) is followed, as in T3. Everything else is T3's: `..` and symlinks out of the root are refused (`resolved_path_outside_root`, symlinks that stay inside are fine), a write never lands in a `.git` or other repository folder, a path is taken as written (whitespace at its ends is part of the name), reads return at most 1 MiB (`truncated` says more existed) and a NUL byte or bytes that are not UTF-8 in what was read mean binary (`binary_file`; a character the 1 MiB cut splits is dropped), a save keeps the byte-order mark the file had (a read decodes it away), `allowMissing` answers `exists: false`, a missing project folder included, directory listings hide `.git`, list a symbolic link that stays inside the root under its target's kind (not one to a folder the listing is inside, so expanding every folder cannot loop), and mark git-ignored entries (a folder's listing through `git check-ignore`, the whole tree's as File search leaves them out; no git marks when `git` is missing or the folder is not a repository). **Last write wins:** the agent may edit the same file at the same time and there is no merge or conflict check, as in T3. Gated by the session's scopes as T3 gates it: `filesystem:read` to list/read/search, `filesystem:write` to write (a standard pairing holds both; a narrowed one, minted in Settings → Sharing & access, may not).

Previewable files are served by `assets.createUrl`; text files still go through `projects.readFile`

### Editor, previews, browser

Control is explicit (`takeControl` / `releaseControl`) and shared between viewers; tabs are capped at 8 per thread and 32 overall, viewers at 4, and the page is closed when its tab closes. A sweep every minute closes tabs with no viewer after 30 idle minutes when they were opened by an agent, or 24 hours when they were opened by the user; a tab with a viewer is kept. The shared browser closes after 3 days with no tabs. With `storageStatePath`, all preview tabs share one context and a durable Playwright storageState file (cookies and origins' localStorage): it loads at start and is written back; `clearProfile` removes it.

Without the path, the browser is ephemeral. There is no T3 profile picker: `reportProfiles` is a no-op. No upload, download or file chooser route. T3 v0.1.5 removed `preview.navigate` and `preview.refresh` from the wire; navigation and reload arrive as preview-stream input. `preview.stopLocalServer` (new in 0.1.5) is refused because `localServerStop` is not advertised.

`shell.openInEditor`, `mcpApps.*` and `subscribeDiscoveredLocalServers` stay refused

### The host's own updates

On this host the provider `pi` is the integrator's agent, so the advisory is the host's. The provider's `version` says the host's own version and then what it is built on, "claw 680f25f, pi 1.6.0, t3 0.1.11" (the integrator's `name` and version, the pi release, the pinned T3 release; without `updates`, the last two). The integrator's comes first because T3's provider list shows about a dozen characters of a version; the provider's own panel shows it whole.

The advisory carries the integrator's version alone: the one that runs, the newest there is (asked of the integrator at start, hourly, and on Settings' Refresh), and the command a person would run. `server.updateProvider` asks the integrator to install, answers T3's provider payload with the update state (`running` on the config stream, then `succeeded`, `unchanged` or `failed` with what the install printed), and a second later asks it to restart; clients reconnect to the new version. Without `updates` the call is refused and the provider carries no advisory.

T3's server update (`server.updateServer`) is another thing, refused below: it brings a T3 server to the client's T3 version and is offered only where the server's is behind

### Scheduled task webhooks

A task with a `webhook` schedule has a URL, `/api/hooks/<task id>/<token>`, and each request to it that passes the task's checks runs the task once, in a new thread or on the task's thread as any run. The prompt is rendered from the request with T3's own template (vendored): `{{body.path}}`, `{{headers.name}}`, `{{query.name}}`, `{{body}}`, `{{request}}`; what came from the request is framed between tags no request can guess and called untrusted, and a placeholder the request has nothing for is left out and named in the delivery log.

The checks are T3's, in its order: the token (a wrong one answers as an unknown hook, 404); a limit of 60 requests a minute a task (429); the task enabled (409); an HMAC-SHA256 signature over the raw body, with the header, encoding and prefix the task names (401); the filters (T3's, vendored: a request they do not match is answered 202 and runs nothing); a replay key (a sender's retry of a delivery that ran is answered 202 and runs nothing, for 7 days); a coalescing window (requests with the same key within it make one run, from the last of them; the window is stored, and the scheduler's poll runs it, so it survives a restart); at most 20 runs waiting a task. Answers carry T3's `x-t3-hook-outcome`. A body over 1 MiB is refused (413).

The task's page reads the last 50 deliveries (at most 20 of them filtered and 20 duplicate or coalesced, as T3 keeps them): the request with its credentials redacted (T3's rule), its body up to 64 KB, the outcome, the prompt it made. Rotating the token gives a new URL; the old one is an unknown hook. A task's token, signing secret, deliveries, replay keys and open windows are one document in the Harness's storage; the secret is not in the task T3 is sent.

The URL a task shows is `webhookOrigin` (an `attachT3` option: where a sender reaches this host) plus the path; without it the task shows the path and T3's client puts its own address in front. The route is served either way: whether a sender on the internet reaches it is the integrator's network.

Not here: T3 Connect's relay, which holds requests for a machine that is offline. Every request arrives directly and now, so `maxDeliveryAgeMinutes` is stored and never skips one, and there is no relay delivery id. Refused by name: `secretRef` on a signature (this host's `request_secret` saves a secret under a name, not as T3's one-use reference; pass `secret`).
